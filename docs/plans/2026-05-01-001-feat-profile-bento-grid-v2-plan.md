# feat: Add profile bento grid v2

Generated by /office-hours on 2026-05-01
Branch: main
Repo: Leeve
Status: DRAFT
Mode: Builder

## Problem Statement

Leeve's current public profile page (`/[handle]`) stores links, social links, text boxes, and playlist widgets in separate legacy tables. Text and playlist also carry `blockPosition`, while the page itself carries `linkBlockPosition`. The new grid system should not replace that page immediately. It should power a new `/v2/[handle]` profile surface with separate bento/layout/content tables.

## What Makes This Cool

The editor can stop being a vertical list with special cases and become a real canvas. A block can be a link group, text card, playlist, profile card, stats card, or future media widget without every new block requiring another top-level ordering scheme.

## Constraints

- Keep `profile_page` as the page owner and public identity source.
- Preserve public read and owner write RLS semantics.
- Do not encode `react-grid-layout` behavior into every content table.
- Support at least two breakpoints: `desktop` and `compact`.
- Keep typed payloads for block-specific content. Avoid one giant untyped JSON blob as the only source of truth.
- Existing profile-page architecture must still move as one unit: schema, validation, query, editor store, sync payload, editor renderer, preview renderer, and public renderer.

## Premises

1. Grid placement is not a property of a link, text box, or playlist. It is a property of a rendered block instance.
2. A block can either own one content record or represent a grouped collection, such as the existing links block containing many `profile_link_item` rows.
3. Breakpoint-specific layout should be stored separately from block content, because `desktop` and `compact` can diverge without changing the content itself.
4. The current `blockPosition` columns are transitional artifacts and should not be the long-term ordering source if grid layout is adopted.

## Approaches Considered

### Approach A: Minimal Bridge

Keep existing content tables and add only `profile_grid_item` plus `profile_grid_item_layout`.

- Summary: Each rendered block gets a row in `profile_grid_item`. Existing tables stay as payload tables. `profile_grid_item_layout` stores `x`, `y`, `w`, `h` per breakpoint.
- Effort: M
- Risk: Low to medium
- Pros:
  - Smallest migration from current architecture.
  - Keeps existing query and sync logic mostly recognizable.
  - Lets the grid prototype ship without forcing all content into a new abstraction at once.
- Cons:
  - Link block remains a special grouped block.
  - Old `position` columns still exist for nested ordering.
  - Requires careful dual-read or migration from `linkBlockPosition` and item `blockPosition`.
- Reuses: Existing `profile_link_item`, `profile_social_link`, `profile_text_box_item`, `profile_playlist_item`, RLS helpers, sync payload patterns.

### Approach B: Ideal Block Registry

Create a canonical `profile_bento` table and make all visible modules children of that bento item.

- Summary: `profile_bento` is the source of identity and type. Layout rows attach to `profile_bento.id`. Type-specific tables use `bentoId` instead of carrying their own layout/order.
- Effort: L
- Risk: Medium
- Pros:
  - Cleanest long-term model for more block types.
  - Makes preview/public rendering a single ordered grid query instead of per-type merging.
  - Removes type-specific `blockPosition` drift.
- Cons:
  - Larger migration and more query/store rewrite.
  - Existing link/social semantics need careful mapping.
  - Overkill if the product only needs a temporary grid demo.
- Reuses: Current content tables after changing ownership from direct page layout to block ownership.

### Approach C: JSON Canvas Snapshot

Store the whole canvas as a JSON document on `profile_page`.

- Summary: One `gridSnapshot` column stores items, layouts, and content references together.
- Effort: S
- Risk: High
- Pros:
  - Fastest prototype path.
  - Mirrors `useGridTestState()` closely.
  - Easy to persist drag/resize state.
- Cons:
  - Weak DB constraints and harder RLS at item level.
  - Harder analytics, migration, dedupe, and public query optimization.
  - Future block-specific validation moves into application code only.
- Reuses: Frontend grid state shape almost directly.

## Recommended Approach

Chosen approach: Approach B. This grid is the new profile-page foundation, so the model should fully separate bento identity, bento layout, and bento content.

Implementation scope decision: Full Bento Graph implementation for the new v2 surface. Create the new bento/layout/content tables and wire them to `/v2/[handle]` and its editor/runtime path. Do not replace the current `/[handle]` public page in this scope.

Rollout decision: additive v2 rollout. Existing `/[handle]` and legacy profile item tables keep working. `/v2/[handle]` reads profile metadata from the existing `profile_page` row and reads the grid area from the new bento/layout/content graph. Any legacy-to-v2 import/backfill is optional migration tooling, not required for the first v2 runtime.

Recommended schema:

```sql
profile_page
  id
  userId
  handle
  name
  location
  role
  bio
  image
  backgroundImage
  createdAt
  updatedAt

profile_bento
  id
  profilePageId
  type -- profile | links | text | playlist | section | stats | ...
  createdAt
  updatedAt

profile_bento_layout
  id
  bentoId
  breakpoint -- desktop | compact
  x
  y
  w
  h
  createdAt
  updatedAt

profile_link_bento
  id
  bentoId
  title
  description
  favicon
  thumbnail
  url
  createdAt
  updatedAt

profile_text_bento
  id
  bentoId
  content
  createdAt
  updatedAt

profile_playlist_bento
  id
  bentoId
  title
  provider
  url
  content
  createdAt
  updatedAt

profile_section_bento
  id
  bentoId
  title
```

Important details:

- `profile_bento` is the shared grid item identity. It contains the page ownership and bento type, not the content payload.
- `profile_bento_layout` contains the bento item's breakpoint-specific position and size.
- `profile_*_bento` tables contain the type-specific content payload.
- Each bento content table should be 1:1 with `profile_bento` via `unique(bentoId)`.
- `profile_bento_layout` needs `unique(bentoId, breakpoint)`.
- `profile_bento_layout` stores only user layout state: `breakpoint`, `x`, `y`, `w`, and `h`. Resize constraints such as `minW`, `maxW`, `minH`, `maxH`, and `isResizable` belong in code config, not the database.
- `profile_bento` needs `index(profilePageId)` and probably `unique(profilePageId, type)` only for singleton bento types like `profile` or `links`. Do not apply that unique rule to repeatable bento types if multiple text, playlist, or section items become possible.
- RLS for `profile_bento` should use the existing page owner boundary. RLS for `profile_bento_layout` and `profile_*_bento` should use new `bentoId`-based helpers, for example `hasProfileBento(bentoId)` and `isProfileBentoOwner(bentoId)`, which join through `profile_bento -> profile_page`.
- Bento child tables should be created as new tables named `profile_{itemType}_bento`, rather than mutating the existing `profile_{itemType}_item` tables in place.
- The new grid system should not use the existing item type tables at runtime.
- Bento content tables should not have `position`. The old `position` columns existed for vertical ordering in the previous system; grid order is now represented by `profile_bento_layout.x` and `profile_bento_layout.y`.
- Existing `profile_link_item`, `profile_text_box_item`, and `profile_playlist_item` tables remain the source of truth for the current `/[handle]` runtime. The new `/v2/[handle]` runtime should not use them.
- Server sync should accept `bento: []` where each bento entry carries its type, breakpoint layouts, and type-specific content. The payload should be grid-item oriented, not table-array oriented.
- The sync payload should not include `linkBlockPosition`, `blockPosition`, or bento `position`.
- `profile_social_item` is intentionally not part of the model. Social links should remain outside this grid item family unless a later product decision makes social a draggable block.

Recommended sync shape:

```ts
type ProfileBentoPayload =
  | {
      id: string;
      type: "link";
      layout: ProfileBentoLayouts;
      content: {
        title: string;
        description: string;
        favicon: string;
        thumbnail: string;
        url: string;
      };
    }
  | {
      id: string;
      type: "text";
      layout: ProfileBentoLayouts;
      content: {
        content: string;
      };
    }
  | {
      id: string;
      type: "playlist";
      layout: ProfileBentoLayouts;
      content: {
        title: string;
        provider: PlaylistProvider;
        url: string;
        content: string;
      };
    }
  | {
      id: string;
      type: "section";
      layout: ProfileBentoLayouts;
      content: {
        title: string;
      };
    };

type ProfileBentoLayouts = {
  desktop: { x: number; y: number; w: number; h: number };
  compact: { x: number; y: number; w: number; h: number };
};
```

Validation decision:

- Use a Zod discriminated union for `bento[]`, keyed by `type`.
- Validate duplicate bento entry ids.
- Require both `desktop` and `compact` layouts for every bento entry.
- Validate `x >= 0`, `y >= 0`, `w > 0`, `h > 0`.
- Validate `x + w <= COLS[breakpoint]`.
- Validate `w/h` against bento-type constraints from grid config.
- Reject content/type mismatch at the sync boundary.

## Open Questions

- Should users be allowed to delete core blocks like profile and links, or only hide them?

## Success Criteria

- Dragging or resizing a bento item updates only layout rows.
- Editing link/text/playlist content does not touch grid coordinates.
- Adding a new bento type requires one new payload table or typed payload handler, not a new page-level ordering system.
- `/v2/[handle]` can render from `profile_bento + profile_bento_layout + profile_*_bento tables` without merging unrelated legacy `blockPosition` fields.
- `/v2/[handle]` must also render existing `profile_page` profile metadata: handle, name, location, role, bio, image, and backgroundImage.
- Validation catches duplicate layout rows per breakpoint and invalid grid bounds.
